# Архитектура оркестратора

Оркестратор выполняет поиск по каталогу UI-компонентов через MCP,
собирает ответ из документации и сохраняет результат каждого запуска.
Управление процессом, доступ к данным и хранение событий разделены на модули.

## Поток данных

```text
CLI: поисковый запрос
  ↓
runTask: создание запуска и переход в running
  ↓
MCP-исполнитель → MCP-клиент → локальный MCP-сервер
                                  ↓
                          component-index.json
  ↓
Ответ из документации → run.json + events.jsonl → вывод в терминал
```

Индексатор создаёт `component-index.json` из исходников `Button`, документации
и метаданных пакета. Сервер читает этот файл по запросу клиента.
Команды установки и запуска приведены в [README](../README.md).

## Последовательность выполнения

1. CLI принимает один непустой аргумент и передаёт запрос в `runTask`.
2. `runTask` создаёт UUID, сохраняет состояние `queued`, затем `running`.
3. Исполнитель запускает дочерний процесс MCP-сервера через клиент.
4. Клиент проходит инициализацию и проверяет наличие двух инструментов.
5. `searchComponents` получает весь поисковый запрос.
6. При наличии совпадения `getComponentDocs` получает имя первого компонента.
7. Исполнитель формирует ответ и закрывает соединение с сервером.
8. `runTask` сохраняет итоговое состояние; CLI выводит результат и пути к файлам.

Порядок вызовов задан кодом. На один запуск приходится один вызов поиска
и, при наличии совпадения, один вызов документации. MCP-клиент задаёт
таймаут 10 секунд для каждого запроса к серверу.

## Модули

Пути в таблице указаны относительно корня репозитория.

| Файл | Ответственность |
|---|---|
| `src/orchestrator/cli.ts` | Аргументы командной строки, вывод и код завершения |
| `src/orchestrator/run-task.ts` | Создание запуска, смена состояний и вызов исполнителя |
| `src/orchestrator/mcp-executor.ts` | Последовательность инструментов и сборка результата |
| `src/orchestrator/types.ts` | Контракты запуска, результата, исполнителя и событий |
| `src/orchestrator/storage.ts` | Сохранение состояния и журнала |
| `src/mcp/client.ts` | Управление процессом сервера, MCP-запросы и проверка ответов |
| `src/mcp/contracts.ts` | Общие схемы ответов клиента и сервера |
| `src/components/schema.ts` | Схема документации компонента и производные TypeScript-типы |

`Executor` принимает запрос и контекст с функцией `record`, затем асинхронно
возвращает `TaskResult`. `runTask` добавляет к событиям исполнителя время
и идентификатор запуска. По умолчанию используется `createMcpExecutor()`;
параметр `executor` позволяет подставить другой исполнитель, например тестовый.

## Состояния и результат

```text
queued → running → completed
                 → failed
```

`completed` означает, что исполнитель вернул результат. Результат поиска
различается полем `outcome`: `found` или `not_found`. При ошибке исполнителя
сохраняются статус `failed` и текст причины; CLI возвращает код 1.

| Поле результата MCP | Содержимое |
|---|---|
| `mode` | Значение `mcp` |
| `outcome` | `found` или `not_found` |
| `component` | Полная запись компонента или `null` |
| `answer` | Текст ответа с API, метаданными и источниками |
| `example` | Примеры из документации; пустая строка при отсутствии компонента |
| `warnings` | Ограничения применения компонента и пояснения к примерам |
| `checks` | Статусы проверки примеров: `props` и `typescript` |

Исполнитель копирует примеры из документации и указывает для них
`checks.props: "not_run"` и `checks.typescript: "not_run"`.
Zod-схемы проверяют структуру данных индекса и ответов MCP.

Клиент также проверяет согласованность результата поиска и документации.
Если между вызовами изменились ID компонента, имя или версия пакета,
исполнитель завершает запуск с ошибкой и предлагает повторить запрос.

## Хранение состояния и журнала

Каждый запуск сохраняется в отдельную папку:

```text
runs/<runId>/
  run.json
  events.jsonl
```

`run.json` содержит запрос, статус, время создания и обновления,
результат либо ошибку. Обновление выполняется через временный файл
и переименование. `events.jsonl` дополняется отдельными строками JSON.

Каждое событие содержит `runId`, `timestamp`, `type` и `message`.
Для вызовов инструментов добавляются имя `tool`, аргументы при старте
и `outcome` при успешном ответе. Время хранится в ISO-формате UTC.

Обычная последовательность событий:

```text
run.created → run.started → executor.started → mcp.connected
  → tool.started → tool.completed                  # поиск
  → tool.started → tool.completed                  # документация при совпадении
  → executor.completed → run.completed
```

При ошибке инструмента записываются `tool.failed`, `executor.failed`
и `run.failed`. Ошибка подключения отражается на уровне исполнителя.

Состояние и журнал записываются отдельно. При разборе аварийного завершения
следует сопоставлять `run.json` с последними событиями журнала.
Ошибки сохранения выводятся в CLI с кодом завершения 1.

## Проверка

```bash
npm run check
npm run test:orchestrator
```

Тесты проверяют переходы состояний, сохранение результатов, изоляцию запусков,
ошибки хранилища и исполнителя, аргументы CLI и интеграцию с MCP-сервером.

Связанные документы: [контракты MCP](mcp-server.md),
[требования и критерии приёмки](requirements.md).
