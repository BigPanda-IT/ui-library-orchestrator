# Шаг 2: каркас оркестратора без модели

## Что мы построили

Программа принимает задачу, создаёт запуск (`run`), вызывает исполнителя,
сохраняет результат и события. Исполнитель пока является заглушкой:
для любого запроса возвращает один демонстрационный ответ про Button.
API-ключ и сеть для запуска не нужны после установки зависимостей.

`completed` означает, что каркас успешно выполнил заглушку и сохранил результат.
Это не подтверждение решения пользовательской задачи. Контрольные запросы
S1–S5 из шага 1 пока не реализованы; проверки примера имеют статус `not_run`.

## Как запустить

В терминале из корня проекта, при установленных зависимостях:

```bash
npm run orchestrate -- "Подбери кнопку для сохранения. Покажи загрузку и пример"
```

Если зависимости ещё не установлены, сначала выполните `npm install`.
Внутри npm-команды выполняется сборка, затем запускается скомпилированный CLI.
`--` отделяет аргументы npm от аргументов нашей программы.
Кавычки передают весь запрос как один аргумент. Пустой запрос и лишние
аргументы отклоняются с кодом завершения 1, без создания запуска.

Справка:

```bash
npm run orchestrate -- --help
```

## Как проходит запрос

```text
CLI: прочитать и проверить ввод
  ↓
runTask: создать runId, сохранить queued
  ↓
runTask: сохранить running
  ↓
mockExecutor: вернуть подготовленный результат
  ↓
runTask: сохранить completed и результат
  ↓
CLI: показать результат и пути к файлам
```

При ошибке исполнителя состояние переходит из `running` в `failed`.
Причина сохраняется в состоянии и журнале; CLI возвращает код 1.
Ошибки файловой системы доходят до CLI: он сообщает об ошибке сохранения
и возвращает код 1. Когда диск недоступен, гарантировать запись `failed` нельзя.

## За что отвечают файлы

| Файл | Обязанность |
|---|---|
| `src/orchestrator/types.ts` | Контракты: что такое запуск, результат, событие и исполнитель |
| `src/orchestrator/cli.ts` | Терминальный ввод, вывод и код завершения |
| `src/orchestrator/run-task.ts` | Порядок действий и смена статусов |
| `src/orchestrator/mock-executor.ts` | Подготовленный демонстрационный ответ |
| `src/orchestrator/storage.ts` | Запись состояния и добавление событий |
| `tests/orchestrator.test.cjs` | Проверки успешного и ошибочного поведения |

`Executor` — функция, которая принимает текст задачи и асинхронно возвращает
результат. `runTask` вызывает её и ждёт через `await`. Это точка замены
заглушки на реального исполнителя. На шаге 3 расширим формат результата
для модели; текущее поле `mode: "mock"` намеренно обозначает только заглушку.

## Состояние и события

Каждый запуск получает UUID и отдельную папку в корне проекта:

```text
runs/<runId>/
  run.json       — последнее сохранённое состояние
  events.jsonl   — последовательность событий
```

`run.json` отвечает на вопрос «в каком состоянии запуск сейчас?».
Он содержит исходную задачу, идентификатор, временные отметки, статус
и результат либо ошибку. Файл обновляется при смене статуса через
временный файл и переименование.

`events.jsonl` отвечает на вопрос «что происходило?».
Каждая строка — самостоятельный JSON-объект с `runId`, временем,
типом события и сообщением. При успехе записываются:

```text
run.created
run.started
executor.started
executor.completed
run.completed
```

Время хранится в ISO-формате UTC. Порядок строк задаёт порядок событий,
даже если некоторые временные отметки совпадают.

## Небольшая практика

1. Запустите команду с запросом про кнопку. Найдите `Run ID` и пути в выводе.
2. Откройте `run.json`: сопоставьте `task`, `status` и `result` с выводом.
3. Откройте `events.jsonl`: проследите запуск по пяти событиям.
4. Повторите команду с другим текстом. Появится другая папка и другой ID.
   Ответ останется прежним: так работает наша заглушка.
5. Запустите `npm run orchestrate` без задачи: программа должна объяснить
   формат ввода и завершиться с ошибкой.

## Проверка реализации

```bash
npm run check
npm run test:orchestrator
```

Тесты проверяют сохранение результата и порядок событий, изоляцию запусков,
ошибку исполнителя, пустую задачу, недоступное хранилище, справку и ошибки CLI.
Исполнитель с ошибкой подставляется только в тесте. Это позволяет проверить
ветку `failed` без поломки обычного демонстрационного запуска.

## Границы этого шага

Пока нет модели, поиска, вызовов инструментов, повторных попыток,
таймаутов, восстановления после прерывания и проверки JSX-примера.
Журнал и состояние — отдельные записи, общей транзакции между ними нет.
При аварийном завершении они могут расходиться, а статус остаться `running`.
На этом этапе мы не заявляем поддержку возобновления таких запусков.

Шаг 2 готов, когда команда создаёт отдельный запуск, возвращает подготовленный
результат и сохраняет последовательность событий. Следующий этап — адаптер модели.
