# Требования к UI Library Orchestrator

UI Library Orchestrator предоставляет через командную строку сведения
о компонентах React/TypeScript-библиотеки: API, правила использования,
примеры и источники. Документ определяет входные данные, ожидаемое поведение
и критерии приёмки приложения.

## Входные данные

Пользователь передаёт один поисковый запрос, например `Button`, `loading`
или `кнопка сохранения`. Необязательный флаг `--docs` выбирает ответ с API,
`--example` — подготовку примера; без флага используется `--example`.
Пробелы по краям удаляются. Пустой ввод, неизвестные флаги и лишние аргументы
CLI отклоняются до создания запуска. Поиск не разбирает произвольные вопросы.

Индекс `component-index.json` создаётся командой `npm run extract` из:

- публичного экспорта и реализации компонента в `src/ui/`;
- объявлений props в `src/ui/Button.types.ts`;
- рекомендаций и примеров в `docs/Button.docs.json`;
- имени и версии пакета в `package.json`.

После изменения этих источников индекс необходимо обновить.
Формат данных определяется схемой `src/components/schema.ts`.

## Функциональные требования

### Индексация

Индекс должен содержать имя компонента, метаданные пакета, способ импорта,
сигнатуру, props и их типы, обязательность, значения по умолчанию,
описания и отметки устаревания. Правила применения, примеры и пути
к исходным файлам должны сохраняться вместе с API.

Генерация должна проверять TypeScript-исходники и структуру результата.
Ошибки входных данных должны завершать команду с диагностикой.

### MCP-сервер

Сервер должен предоставлять инструменты `searchComponents` и `getComponentDocs`
через транспорт `stdio`, публиковать схемы их аргументов и результатов
и проверять входные параметры.

Поиск должен сопоставлять все слова запроса с именем, описанием,
ключевыми словами, назначением и именами props. Получение документации
должно использовать точное имя компонента с нормализацией регистра.

Каждый вызов должен читать и проверять индекс. Пустая выдача и ошибка
чтения файла должны возвращаться как разные исходы.
Подробные форматы приведены в [контрактах MCP](mcp-server.md).

### Оркестратор

Оркестратор должен:

1. Создать уникальный идентификатор запуска и сохранить исходный запрос.
   Сохранить выбранный маршрут в состоянии и журнале.
2. Подключиться к MCP-серверу и обнаружить необходимые инструменты.
3. Выполнить поиск и получить документацию первого совпадения.
4. Сформировать ответ из полученных данных и примеров документации.
5. Закрыть соединение с сервером после выполнения, включая обработку ошибки.
6. Только на маршруте `example` для локального Button подготовить пример сохранения с loading и onClick.
7. Сохранить TSX, проверить props по MCP и типы по локальному исходному коду.
8. Сохранить результат, диагностику, состояния и события.
9. При замечаниях передать предыдущий код и диагностику подготовщику; выполнить
   не более двух доработок и сохранять каждую попытку.

Количество вызовов инструментов ограничено двумя: поиск и документация.
Таймаут каждого запроса MCP-клиента составляет 10 секунд.

## Требования к результату

CLI должен выводить идентификатор запуска, статус, ответ
и пути к файлам состояния и журнала.

При найденном компоненте результат должен содержать:

- имя, версию пакета и источники документации;
- публичный API и рекомендации по использованию;
- исходные примеры в `component.examples`, подготовленный TSX в `example`;
- предупреждения об устаревших props и ограничениях компонента;
- отдельные поля статуса проверки props и TypeScript.

На маршруте `docs` поле `example` пустое, файлы примера не создаются,
проверки имеют статус `not_run`, подготовщик и проверяющий не вызываются.
Исходные примеры остаются в полной документации `component.examples`.

Для подготовленного примера проверки имеют статус `passed` или `failed`.
Диагностика содержит вид проверки, код, серьёзность, сообщение и, если доступно,
файл со строкой и колонкой. Ошибки неизвестных и обязательных props блокируют
успех; устаревшие props дают предупреждения. JSX spread отклоняется с явной
диагностикой. Типы значений и обработчиков проверяет TypeScript.
Проверяющий возвращает `needs_changes` и для устаревших props, даже если обе
проверки типов имеют статус `passed`. Подготовщик заменяет `isPending` на
`loading` лишь при наличии подходящих записей в документации, без конфликтующего
`loading`, повторных атрибутов или spread. Остальные замечания не исправляются
автоматически. При повторении кода и замечаний или исчерпании двух доработок
оркестратор завершает запуск с причиной и статусом `validation_failed`.

Файлы `example.tsx`, `tsconfig.json` и `validation.json` должны сохраняться
в папке запуска. TypeScript выполняется без генерации JS и без запуска примера.
Сохранённая конфигурация должна позволять повторную проверку через `npx tsc -p`.
Ошибка проверки даёт `validation_failed` и код CLI 1 с сохранением результата.

Шаблон поддерживает локальный `Button` с экспортом `src/ui/index.ts` и всегда
описывает сохранение. Приложение передаёт функцию `onSave`; адаптации к смыслу
запроса нет. Для других компонентов возвращаются примеры документации,
пояснение об отсутствии шаблона и статусы `not_run`.

При отсутствии совпадений результат должен содержать `outcome: "not_found"`,
`component: null` и пустую строку примера. Запуск при этом получает
статус `completed`. Техническая ошибка должна давать статус `failed`,
причину в состоянии и журнале и код завершения CLI 1.

## Критерии приёмки

Сценарии выполняются с индексом компонента `Button`, созданным из репозитория.

| Сценарий | Ожидаемый результат |
|---|---|
| Запрос `Button` | Документация компонента, `completed`, `outcome: "found"` |
| `--docs "Button"` | API через MCP без подготовки и проверки примера |
| `--example "Button"` | API через MCP и подготовка проверенного примера |
| Запрос `кнопка сохранения` | Поиск `Button`, затем получение его документации |
| Запрос `DatePicker` | `completed`, `outcome: "not_found"`, пустой пример |
| Пустой запрос CLI или лишний аргумент | Код 1; запуск не создаётся |
| Поисковый запрос `!!!` | Ошибка валидации инструмента, запуск `failed` |
| Отсутствующий или повреждённый индекс | Техническая ошибка с причиной, запуск `failed` |
| Изменённые описание и примеры в валидном индексе | Ответ содержит обновлённые данные |
| Два независимых запуска | Разные идентификаторы и отдельные файлы результатов |
| Ошибка инструмента | В журнале есть имя инструмента и причина ошибки |
| Успешный поиск | Журнал показывает аргументы и исходы поиска и чтения документации |
| Корректный пример Button | Файлы сохранены, props и TypeScript имеют статус `passed` |
| `size="large"` в примере | `UNKNOWN_PROP` и ошибка TypeScript с позицией |
| Отсутствующий children | Диагностика обязательного prop и ошибка TypeScript |
| `loading="yes"` | Проверка props успешна; TypeScript отклоняет тип значения |
| `isPending={true}` | Предупреждение `DEPRECATED_PROP` |
| Индекс не содержит используемого loading | `validation_failed`, результат и диагностика сохранены |
| `isPending` без конфликта | Замена на `loading`, повторная проверка, сохранены оба варианта |
| `isPending` и `loading` вместе | Остановка: исправление неоднозначно |
| Та же ошибка после доработки | Остановка с причиной повторения |
| Две неудачные доработки | Остановка по лимиту, сохранён последний вариант |

## Проверка требований

```bash
npm run check
npm test
```

`tests/mcp.test.cjs` проверяет протокол, поиск, документацию,
валидацию аргументов и ошибки индекса. `tests/orchestrator.test.cjs`
проверяет CLI, хранение состояния, журнал и сквозное выполнение через MCP.
Workflow `.github/workflows/ci.yml` запускает `npm ci`, `npm run check` и
`npm test` на GitHub Actions при push, pull request и ручном запуске.
Последовательность для демонстрации и ожидаемые результаты описаны в
[сценарии демонстрации](demo.md).

Порядок выполнения и ответственность модулей описаны
в [архитектуре оркестратора](architecture.md).
